## Implemented

- Appended `0027_explorers_lifecycle.sql` and advanced the migration/deployment marker, exact file lists, runtime grants, fixture table manifest, route inventory, authorization matrix and policy tests. Existing migrations remain unchanged. Canonical account routes now derive ownership from the verified Better Auth Actor, persist bounded trimmed deletion feedback with account-scoped idempotency, require current revision and owned feedback for deletion, and commit suspension/pending deletion plus session revocation atomically. Requests with another account's feedback ID, malformed input, a reused key with changed payload, or an old revision fail.
- The qualified 2.1 Google callback/recovery proof hook is reused. Recovery resolves a server-only principal bound to the existing Google subject, account, session and five-minute single-use proof; it never grants ordinary Actor authority. Recovery and pending-deletion cancellation consume the proof in the account transition transaction, fence a second concurrent consumer, reject wrong identity/expired/revoked/replayed proof and terminal deletion, and require a fresh ordinary session for content access. No public test-login route was introduced.
- The browser now uses cookie-backed Better Auth plus canonical `/me` before granting private routes. Explicit loading, signed-out, active/incomplete, active/complete, recovery-only, terminal and retryable-error states replace localStorage Strapi JWT authority. Generation fences prevent delayed A→B→A responses, navigation and Settings callbacks from affecting a new session. Login, callback, protected/guest routes, OnBoarding, Home, Favorites, Profile, setup state, category navigation, Settings and recovery screens use this boundary. The Google-only login/recovery screens are the agreed visible parity exception; password/email token forms redirect to Google. Legacy URL tokens confer no authority.
- One logout coordinator synchronously fences local access, notifies tabs, clears account-scoped React Query/Apollo/Music/setup state, closes Music sockets and ends the server session. Failed server signout remains visible and retryable. Simultaneous definitive 401 responses cause one generation transition; 403, 404 and transport outages preserve the current session. Global Apollo bootstrap no longer sends `qrtoken` or canonical credentials to retained Strapi category reads. The Settings wizard retains its required reason, error and retry steps while writing through the canonical feedback and lifecycle routes; its active path does not issue Strapi deletion mutations.

## Remaining gates and limits

- **Live Google acceptance remains open.** No `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` was present in the test environment, so no configured development Google callback was performed. The qualified provider callback tests are simulations, and the real API browser tests use synthetic linked identities. Do not mark the ticket fully accepted on these results alone.
- The pending-deletion transition locks ordinary access and revokes sessions but does not yet execute the terminal owner-content purge or publish server-side socket disconnection. The ticket explicitly assigns socket-disconnection acceptance to 6.1. A deletion retention policy and worker are still required before production: keep feedback reason restricted to the account/lifecycle process, purge raw reason at terminal deletion (and bound abandoned pending feedback to at most 30 days), and retain only a minimal non-content tombstone/receipt needed to prevent Google re-provisioning. The new schema permits `reason=NULL,purged_at` for that purge but does not schedule it. Terminal no-resurrection is covered by recovery tests; terminal finalization itself is a later gate.
- Retained Apollo category UI still calls Strapi for category data, but its calls carry no canonical cookie/bearer or `qrtoken`. The dormant legacy lifecycle service/API definitions remain in source for compatibility; no active Settings path invokes them. Category conversion/retirement remains in later tickets.
- The Windows deployment shell executable suite did not finish in a bounded broad run and remains an explicit verification gap; its changed marker has a passing syntax check and the focused file/readiness contract checks below, but those do not replace the executable suite.
